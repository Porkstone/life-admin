Migration plan · 24 July 2026

Move the Life Admin frontend to Vercel

Keep all data, functions, authentication, file storage, and email actions on the existing Convex backend. Vercel will serve only the compiled Vite/React frontend.

Small code change No data migration Low-risk cutover Backend remains Convex

Target architecture

User browser Loads the SPA and follows invite/password-reset deep links.
→
Vercel Builds and serves the static Vite frontend from its CDN.
→
Convex Continues to provide auth, realtime data, functions, HTTP routes, storage, and Resend actions.

Current-state assessment

Already separated

The app is already Vite/React in src/ with Convex functions in convex/; no framework rewrite is required.

Correct client variable

src/main.tsx already expects VITE_CONVEX_URL, which the Convex deploy command can inject during the Vercel build.

Deep links need a rewrite

/invite/:token and /reset-password/:token require a Vercel SPA fallback to /index.html.

One same-origin dependency

fetch("/reset-password") would call Vercel after the move, not the Convex HTTP endpoint. This must be decoupled before cutover.

Implementation plan

  1. 1. Establish a deployable repository baseline

    Put this directory in a Git repository that Vercel can import. Stop ignoring package-lock.json and commit it so installs are reproducible. Record which Convex deployment is production; the README currently names colorless-chickadee-470.

  2. 2. Remove assumptions that frontend and backend share an origin

    • Replace the relative password-reset HTTP call with the existing Convex mutation through the Convex React client. This avoids a Vercel proxy and browser CORS configuration.
    • Introduce a backend environment variable such as APP_URL for links generated in emails, and set it to the final Vercel/custom-domain origin.
    • Keep CONVEX_SITE_URL in convex/auth.config.ts; it identifies the Convex auth issuer and should not be changed to the Vercel URL.
    • While touching the reset email, replace the hard-coded recipient with the requested email and confirm the Resend sender is valid for production.

  3. 3. Add repository-owned Vercel configuration

    • Add a vercel-build script in package.json that runs convex deploy --cmd-url-env-var-name VITE_CONVEX_URL --cmd "npm run build". Configure Vercel to use that script so every production frontend build deploys the matching Convex backend first.
    • Add vercel.json with the build command and a catch-all rewrite to /index.html for direct visits to SPA routes.
    • Optionally remove the Chef-only development injection from vite.config.ts once Chef previews are no longer used.

  4. 4. Configure Convex and Vercel

    • Generate a Convex production deploy key with deployment permission and add it to Vercel as CONVEX_DEPLOY_KEY, scoped to Production only.
    • Set APP_URL on the Convex production deployment to the canonical Vercel URL. Keep backend-only secrets such as CONVEX_RESEND_API_KEY in Convex, not Vercel.
    • Import the Git repository into Vercel, confirm the framework preset is Vite, and deploy from the production branch.

  5. 5. Verify, cut over, and retain rollback

    • Run type checks and a production build before deployment.
    • Smoke-test sign-in/out, realtime CRUD, file upload/download, invite creation/acceptance, password-reset email, and password reset.
    • Hard-refresh both tokenized routes to prove the SPA rewrite works.
    • Check Vercel build logs and Convex production logs, then move the custom domain—or begin using the Vercel URL.
    • Leave the old Convex-hosted frontend available briefly. Rollback is simply returning traffic to it or restoring the previous Vercel deployment; Convex data is never moved.

Environment ownership

Variable Where it lives Purpose
CONVEX_DEPLOY_KEY Vercel secret Allows CI to deploy functions to the selected Convex production deployment. Never expose it to the browser.
VITE_CONVEX_URL Build-time injection Public Convex client URL. Let convex deploy inject the URL for the deployment being built.
APP_URL Convex environment Canonical frontend origin used to generate invite/reset links, for example https://life-admin.vercel.app.
CONVEX_RESEND_API_KEY Convex environment Existing backend-only email secret; no change in ownership.
CONVEX_SITE_URL Convex runtime Convex HTTP/auth origin. Do not repurpose this as the Vercel frontend URL.

Acceptance criteria

  • The production URL serves the frontend from Vercel while all application data remains in the intended Convex production deployment.
  • A production Git push deploys both the Convex functions and the matching Vite bundle.
  • Direct navigation and refresh work for /invite/:token and /reset-password/:token.
  • No browser request incorrectly sends a backend route to the Vercel origin.
  • Generated emails use the canonical frontend URL and complete the reset flow successfully.
  • Secrets are present only in their owning server-side platform and are absent from the frontend bundle.

Recommended rollout: deploy to the default *.vercel.app URL, complete the smoke test, then attach the custom domain. Do not retire the existing Convex-hosted frontend until the reset and invite flows pass.

Questions to confirm before implementation
